# ForgeCare AI

Local, Python-only ILP prototype based on `Federated_Equipment_Health_BRD_v3-1.docx`. It joins live camera evidence, reviewed visual labels, an explainable inspection queue, model comparisons, FedAvg exercises, and cited manufacturer guidance in a Streamlit interface. The demo inspection subjects are an **iPhone 14 Plus** and a **realme narzo 60 5G**, each with separate asset, model, and knowledge scope. The **Samsung Galaxy S24 FE is a separate live camera source**, not an inspection subject. The product scenario remains manufacturing and automotive equipment. Phone results do not validate an automotive deployment.

## Start on Windows

1. On this prepared laptop, run `powershell -ExecutionPolicy Bypass -File .\start-laptop.ps1` from this folder. It reuses the prepared Python 3.14.7 environment. On another Windows computer, install **64-bit Python 3.14.7** and run `powershell -ExecutionPolicy Bypass -File .\run.ps1`; the launcher checks the exact version, creates `.venv`, and installs `requirements.txt`. Use `run.ps1 -Install` to refresh dependencies. See [PyCharm setup](docs/TCS_PYCHARM_3147.md) for the ZIP transfer and interpreter steps.
2. Open `http://127.0.0.1:8501`. On this prepared laptop, sign in with the current administrator password. `%LOCALAPPDATA%\ForgeCareAI\first-login.txt` holds only the original password and will no longer work after a password change. On a fresh installation, create the first administrator on the setup screen.
3. On the **local** `http://127.0.0.1:8501` page, open **Live cameras**, select **Lenovo built-in webcam**, and press **Start selected camera**. ForgeCare switches that camera to local device index `0` and saves a new frame about every five seconds; no browser photo widget or permission dialog is involved. To use the Samsung on the same Wi-Fi, start IP Webcam on it, select **Samsung IP Webcam** in the same local page, enter the phone's current HTTP `http://IP:8080` address, and press **Start selected camera**. ForgeCare reads `/video` directly without a bridge. The preview shows only fresh frames and labels clear, blurry, dark, or bright images; the quality check tests focus and lighting, not whether a defect is present. Stop the selected camera when finished. The laptop and Samsung must be able to reach each other on the local network.

   On the **hosted** page, source `browser` uses the camera on the device opening that page. In **Live cameras**, press **Start this computer's camera** once and allow browser access. The preview stays live and saves frames about every five seconds; there is no repeated Take Photo step. Press Stop when finished. A `0` source on the hosted page still refers to the *hosting server's* webcam. Saved photos remain in Capture review.
4. A **Samsung IP Webcam direct stream** on the hosted page works only when the Samsung and the *hosting laptop* share reachable Wi-Fi. Enter the phone's current HTTP `http://IP:8080` address in **Live cameras**, then press **Start Samsung stream**. ForgeCare checks reachability before opening `/video`. If the phone shares Wi-Fi with the viewing laptop but not the hosting laptop, the hosted server cannot read its private IP; run the local installation on that viewing laptop instead. No separate IP Webcam bridge is needed. New frames appear in **Live cameras** and **Capture review** with server-computed brightness and focus checks. Dent detection remains disabled after failing its held-out check; per-photo model suggestions are not confirmed damage counts.
5. In **Capture review**, choose a usable photo, select up to five distinct photos from the same camera, session, asset, and physical sample within five minutes, and label their views. Use at least two views when available; a single-photo draft remains possible. Click **Build draft from selected photos**, then **Analyze selected photos for visible damage**. The screen shows the real load, per-photo inference, and summary stages with measured model times and a brief pause for readability. It displays an overlay and finding table for every view, fills an editable written review, and suggests the largest single-view scratch count in the editable scratch field. The local model cannot establish a dent count. Optionally click **Generate AI review from selected photos** to send up to three images to Groq for a structured tentative description and scratch/dent counts *only where the images visibly support them*; an uncertain count remains blank. That response also fills the editable note and supported count fields. Compare all images yourself, correct the draft, select `none`, `minor`, `significant`, or `unclear`, and confirm the count fields only after checking the photos and physical phone. A required checkbox blocks saving an AI-assisted review until the technician checks it. The same mark can appear in several views, so never add per-photo suggestions into a phone total. Unusable captures can only be marked `unclear`. **Capture review** also has fictional practice reviews that are never saved.
6. Saving a clear technician review now opens or reuses a work order for **that exact photo**. Go to **Inspection queue** to see the newest active order first. Older clear reviews that were previously left unlinked appear under **Reviewed photos awaiting a work order** with an **Add this reviewed photo** button. Distinct reviewed photos can each have a distinct order even if one phone asset already has an approved order; pressing the button twice for the same photo reuses its existing order. Unclear reviews require recapture and do not enter the work-order queue. The work order shows the equipment, saved photo, visible-condition label and note, technician-confirmed counts, assignment, approved instructions, and recorded outcome. The attention level orders work; it is not a diagnosis. A supervisor assigns and approves clear instructions. **Approve inspection** changes the stage to **Ready to inspect**; it does not complete the work. Select that order, scroll to **Finish this inspection**, enter the actual finding and minutes, indicate whether the physical phone was inspected, and click **Save finding and complete work order**. The stage then reads **Completed**. Mark a physical inspection only after inspecting the phone itself. If one camera is moved to the other subject, stop its worker and save the new asset and distinct physical sample ID before restarting. The API rejects frames from an old asset/sample mapping.
7. **Live cameras** reports **Live** only while fresh frames arrive. **Offline** means the worker or source has failed, **No live signal** means fresh frames stopped arriving, and **Stopped by operator** means the worker was deliberately stopped. The last-frame timestamp is saved history, not a current feed. **Audit** displays business activity with the time, actor, record, and plain-language outcome; its CSV export has the same readable columns.
7. The prepared laptop has already indexed the [iPhone 14 Plus repair manual](https://support.apple.com/en-us/100322), its [battery procedure](https://support.apple.com/en-us/100346) and [back-glass procedure](https://support.apple.com/en-us/100328), the [broken glass safety page](https://support.apple.com/en-us/100298), [realme narzo 60 specifications](https://www.realme.com/in/realme-narzo-60/specs), and [realme support FAQ](https://www.realme.com/in/support/faq). Search these in **Knowledge assistant**; the agent can prepare a draft for supervisor review. The specific Apple procedures support a cited overview and link to the complete guide, while Realme specifications are product facts rather than a repair procedure.
   The hosted knowledge assistant also indexes reviewed Apple battery, Android screen/charging, NIST manufacturing, and AIAG automotive quality pages. **Automatic** question routing covers the selected phone, manufacturing, and automotive quality; the question-area selector can override it. General pages do not become model-specific repair instructions. Answers must cite the approved source passages; if generation is unavailable, the chat shows short related excerpts and source links. Unknown exact component specifications are withheld. Rebuild the curated general source set on a fresh installation with `python -m scripts.index_general_knowledge --site YOUR_SITE_ID` after starting the knowledge service. The approved HTTPS hosts are limited in `forgecare/knowledge_api.py`; indexing is never open web search.
8. **Models & experiments** leads with genuine Renault Group AutoVI automotive pipe-clip images. Its normal-only PaDiM model caught 67 of 71 held-out staged defects, but falsely flagged 67 of 98 acceptable clips. A separate **actual Flower** run used two in-process clients on an adapted supervised AutoVI split; it caught 19 of 21 held-out defects but falsely flagged 30 of 60 acceptable clips. Its split differs from PaDiM, so the numbers are not directly comparable. A cast pump impeller Flower study and two phone side studies are also shown. The newer phone detector reports candidate broken and scratch regions per photo; dent detection is disabled because it found none of 14 labeled dent regions in its held-out check. It has not been validated on the iPhone 14 Plus or realme narzo 60. **Federation** shows the latest scheduled phone attempt and the completed automotive Flower run's start, finish, client counts, and three rounds. All candidates remain research only. See [research data, exact paths, metrics, and reproduction](docs/RESEARCH_AND_DATA.md).

The cast impeller section translates its held-out result into worker queue size, missed defects, unnecessary rechecks, and an editable time/cost scenario. Enter your own plant assumptions; no production saving or return on investment has been measured.

### Six-hour phone federation check

On this prepared laptop, the Windows task **ForgeCareAI Phone FedAvg** runs `run-phone-federation.ps1` every six hours while this Windows account is signed in and the laptop is available. It attempts a separate model for iPhone 14 Plus and realme narzo 60 5G, saving attempt reports and any completed combined models in the `scheduled_federation` folder under the data path recorded in `.phone-federation-data-path`. That path accounts for this laptop's Codex AppData virtualization. The **Federation** page shows when the latest attempt ran, each subject's distinct reviewed-phone counts, skip reason or three-round timeline, and held-out agreement with technician labels. A run requires at least **six distinct acceptable and six distinct damaged physical phones per model**, plus 24 reviewed usable photos; repeated frames of one phone do not meet that gate. The current subjects do not meet it, so the first attempt correctly recorded skips and produced no phone model. When enough reviewed phones exist, the task uses two disjoint logical clients **on this laptop**, combines their weights for three rounds, checks held-out phone groups, and saves the full model locally. It does not send a model to another computer or claim cross-site privacy. Use `powershell -ExecutionPolicy Bypass -File .\run-phone-federation.ps1` for an immediate attempt. Use `install-phone-federation-task.ps1` to reinstall the six-hour Windows task.

### Optional Groq answers and visual drafts

Set a Windows **user** environment variable named `GROQ_API_KEY` using *Edit environment variables for your account*, then restart ForgeCare with `stop.ps1` and `start-laptop.ps1`. The assistant generates conversational answers only when it can cite approved indexed passages. Without a usable key, it shows source passages without a cloud-generated answer. The visual draft button sends at most three selected photos to Groq's vision endpoint; the local damage detector does not send photos to that service. The worker must verify and edit either draft. Model access and free-tier limits depend on the Groq account. The app does not send images merely by opening Capture review.

Use `.\stop.ps1` to stop the three app processes. Logs and data are stored in `%LOCALAPPDATA%\ForgeCareAI\data` by default. Set `FORGECARE_DATA` to choose another private location. To use an existing environment: set `$env:FORGECARE_PYTHON` to its `python.exe` before running `run.ps1`.

To try the queue before any camera captures exist, open **Inspection queue** and leave **Explore with sample cases** on. Adjust **Available inspection minutes** to see the same capacity rule select from four clearly labeled illustrative cases. The sample cases are never written to the operational database. Turn the preview off to see only real inspection cases.

For the prepared laptop installation, the original administrator sign-in is in `%LOCALAPPDATA%\ForgeCareAI\first-login.txt`. Change that password in **Administration** after your first sign-in; the app invalidates existing sessions when it changes.

For a reviewed RAG retrieval evaluation, create `rag_gold.csv` inside the runtime data folder with `question,family,model,relevant_passage_id` columns and at least five manually checked rows. Passage IDs appear in the Knowledge assistant. Without that file, the suite records `insufficient_data`.

## Architecture and boundaries

- Server 1: `forgecare.ops_api` on port 8000. SQLite operational records, site-scoped roles, queue, model registry, FedAvg workbench.
- Camera relay: `forgecare.relay_api` on port 8502. The fixed public gateway forwards `/camera-relay/*` through the authenticated laptop bridge, so no changing camera tunnel address is needed. It exposes only a paired camera configuration, capture, and connection status. Pair codes expire after two hours and are revoked when the camera mapping changes. The host laptop must stay powered and online.
- Server 2: `forgecare.knowledge_api` on port 8001. Approved-source ingestion, site/model/revision filtering, TF-IDF plus optional MiniLM/FAISS retrieval, optional Groq generation with citation validation, local Qwen2.5-0.5B fallback, bounded LangGraph agent.
- Streamlit: port 8501. OpenCV workers send only camera events to Server 1. Each worker requires a configured device index or live network stream. Raw images stay in this installation's `data/images` folder.

The app's original two-client exercise uses a **synthetic, same-machine fixture**. Separately, the completed [automotive and cast impeller research runs](docs/RESEARCH_AND_DATA.md) used real images and Flower FedAvg on two disjoint in-process clients each. Neither establishes cross-factory privacy or phone accuracy. The local LLM and embedding weights download on first use; an offline or insufficient-memory run returns retrieval-only or unavailable status. Groq is optional and subject to its current access limits.

### Real client weight exchange

The **Federation** page can create a model-specific round. On each client computer, prepare a reviewed CSV manifest with `image_path,binary_label,sample_id` columns; paths can be relative to the manifest. Use one row per genuine captured image and keep each physical phone's sample ID stable. Each client needs both labels and several physical samples per class so a grouped held-out split can be formed. Raw images remain on that computer.

Set `FORGECARE_PASSWORD` in the client shell, then run:

```powershell
python -m forgecare.federated_client train --round ROUND_ID --site SITE_ID --client CLIENT_A --manifest .\reviewed.csv --username REVIEWER
```

Repeat on a second client with a different client ID. A reviewer aggregates once both updates appear in the dashboard. Then each client runs the same command with `validate` in place of `train`. The server records local and combined recall, false-alert rate, sample counts and latency for every client. A candidate enters the model registry only if every participating client passes the configured gate, and a reviewer must explicitly approve it. Client-reported metrics are not independently attested in this local prototype.

The product requires more data before operational effort estimates, forecasts, and visual model deployment. In particular, collect multiple distinct physical samples per class, real inspection durations, and regular measured condition histories. The camera and document source paths should be configured for the customer's actual equipment before a pilot.

## Verification

Run `python -m pytest -q` inside the environment. Tests cover the case lifecycle, stale event rejection, site access, duplicate handling, capacity selection, and FedAvg invalid updates. Curriculum exercises use sklearn digits or synthetic fixtures and are labeled in every result. Their scores are not equipment performance claims.

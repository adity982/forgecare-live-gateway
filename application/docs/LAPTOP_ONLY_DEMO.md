# Laptop-only live demo

## Using the hosted link from another laptop or the Samsung

The hosted page runs on the home laptop, but **Live cameras → Take photos on this device** opens the camera in the browser of the device viewing that page. Set the appropriate camera record's source to `browser` in **Assets & setup** first. For the realme, choose `camera-laptop`; for the iPhone, choose `camera-samsung`. Open the HTTPS link on the laptop or Samsung, sign in, click **Enable this device's camera**, then the camera widget's **Take Photo** control. Allow camera access and save each photo. The same captured photos then appear in **Capture review** and can be reviewed together. The browser controls the permission prompt; if access was previously denied, reset that site's camera permission. This is manual photo capture, not an automatic video stream.

IP Webcam at `http://10.106.27.223:8080/video` timed out from the home server on 2026-11-06. It is a private address on a different Wi-Fi network; changing the camera record's IP does not make the server able to reach it. To use IP Webcam from the hosted page, enter the phone's **current HTTP** address under `camera-samsung` in **Assets & setup**. Do not enter the HTTPS address. Open the **Test moving phone video on this laptop** link in the physical laptop's browser, outside the TCS emulator, while the phone and laptop are on the same Wi-Fi. Generate a pairing code and download `ip_webcam_bridge.py` from the page. Run the shown Python command on that physical laptop and enter the code. The bridge reads `/shot.jpg` or `/video` locally and sends photos over the separate HTTPS relay. The resulting status appears in **Live cameras**. Stop the bridge with Ctrl+C when done.

## Using both sources on the same local network

This is the first two-camera path. It uses the Lenovo laptop webcam and the **Samsung Galaxy S24 FE as a Wi-Fi camera**. The inspection subjects are the **realme narzo 60 5G** and **iPhone 14 Plus**. No Raspberry Pi, HDMI cable, or USB camera is needed. Both subject assets, official source documents, and both camera records are prepared. The Samsung's `/video` stream was reachable from the laptop and read as a 720×480 OpenCV frame on 2026-11-04. Neither camera worker starts automatically; live capture in ForgeCare still needs to be verified with each subject in view.

## When the phones and laptop are together

1. Start the app with `powershell -ExecutionPolicy Bypass -File .\start-laptop.ps1` from the release folder if it is not already running, then open `http://127.0.0.1:8501` on the laptop. Sign in with the current administrator password. `%LOCALAPPDATA%\ForgeCareAI\first-login.txt` contains only the original password; it will not work after a password change.
2. On the Samsung S24 FE, install [IP Webcam](https://play.google.com/store/apps/details?id=com.pas.webcam), allow camera access, and choose a moderate video resolution such as 720p for the first connection test. Connect the Samsung and laptop to the same Wi-Fi. In the app, select **Start server** and note the local address displayed on the phone. Append `/video` to that address, for example `http://192.168.1.23:8080/video`; this is an example, not your actual URL. Keep the app open and the Samsung on a stable stand. Use local streaming rather than optional cloud broadcasting. The [IP Webcam connection example](https://www.mathworks.com/help/matlab/supportpkg/acquire-images-from-an-ip-camera-android-app.html) documents this URL pattern.
3. On the laptop, open the Samsung's exact `/video` URL in a browser. Confirm it displays a **moving live view**. `camera-samsung` is registered against `iphone-14-plus` with sample ID `iphone-physical-01`; check its source in **Assets & setup** and update it if the phone's Wi-Fi address changes. Do not register the Samsung as an asset: it is a camera, not an inspection subject.
4. Open the Lenovo webcam privacy shutter, if closed. Confirm `camera-laptop` uses source `0`, subject `realme-narzo-60`, and sample ID `realme-physical-01`. Position the realme in the Lenovo camera view and the iPhone in the Samsung camera view, with steady lighting and a plain background.
5. Start each worker from **Assets & setup**. **Live cameras** updates every five seconds and puts live sources first. Check the capture timestamp and **Recent photos received** count to confirm new frames are arriving; a stationary phone can make consecutive images look similar. Get at least two usable views of the phone. Image-quality checks count usable photos. General visual-model alerts appear only when an approved model is installed; scratch and dent counts remain unavailable until a validated detector exists. If a frame is `blurred`, `dark`, or `bright`, improve positioning or lighting. A connected camera is demonstrated only when its actual frames arrive in ForgeCare. Stop the worker in **Assets & setup** when done, even if IP Webcam has already stopped.
6. In **Capture review**, keep **Show captures** on **Usable images**, select a clear view of one subject, then select up to five distinct photos and name each view. Choose at least two when available; a single-photo draft is allowed. The candidates are restricted to that camera session and physical sample within five minutes. Click **Build draft from selected photos**. Inspect every supporting photo, write **Technician's corrected review**, and enter a visible scratch/dent count only if you personally verified it. Leave an unassessable count blank. If the chosen photo does not show enough detail to judge the condition, choose `unclear` or recapture even when its automatic quality says `ok`. Save a clear review; the app creates or links the work order for that photo. In **Inspection queue**, approve and close with the actual finding and time. Older saved reviews without an order appear under **Reviewed photos awaiting a work order** for one-click addition. The score is review priority, not a failure probability. The separate fictional practice reviews are for UI exploration only.
7. Stop both workers in **Assets & setup** before stopping IP Webcam on the Samsung. Review the indexed Apple and realme sources in **Knowledge assistant**. An answer may be retrieval-only when the local model cannot provide a valid citation; check the linked excerpts before using any guidance.

## If both cameras inspect the same phone

For two angles of one subject, stop both workers before changing mappings. Map both cameras to that subject's asset and use the **same physical sample ID** for both views. Inspect the other subject in a separate session, again changing mappings only while workers are stopped. Keep the Samsung as a camera throughout.

## If no frame arrives

- Check that the webcam shutter is open and Windows allows desktop apps to use the camera.
- Check that no video-call app has taken exclusive control of the webcam.
- Check the registered camera source and the latest camera error in **Live cameras**. Logs are in `%LOCALAPPDATA%\ForgeCareAI\data\camera-camera-laptop.log` and `camera-camera-samsung.log` after each worker is started.
- Keep the Samsung and laptop on a Wi-Fi network that permits device-to-device connections. Verify the exact live URL in the laptop browser before starting its worker. Keep the Samsung app in the foreground and the phone sufficiently charged. A saved video file is not accepted as a live source.
- If **Capture review** shows a black frame, it is saved evidence from a covered or dark camera view; changing the condition label cannot repair it. Select **Usable images** and choose a frame showing the phone, or restart the phone stream, reposition it, and capture again. The worker now exits after three near-black frames or repeated disconnections. Poor-quality captures can only be labeled `unclear` and cannot open cases.

One physical phone per model supports a live workflow demonstration but cannot provide an independent model accuracy estimate. Additional distinct, reviewed samples of each model and both condition classes are needed for training and validation.
